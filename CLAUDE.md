# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Vue d'ensemble

`opendata-vda` est un portail de données ouvertes pour un territoire unique : la commune de Val-d'Aigoual et son EPCI (CC Causses Aigoual Cévennes – Terres Solidaires, Gard). C'est un monorepo pnpm (`apps/*` + `packages/*`) avec 3 apps et un package partagé, aucune suite de tests ni linter n'est configurée à ce jour.

## Commandes

- `pnpm install` — installe les dépendances (pnpm 11.10.0 pinné dans `packageManager`, workspaces `apps/*` + `packages/*`).
- `pnpm dev:web` / `pnpm dev:api` / `pnpm dev:worker` — lance chaque app en mode dev (`astro dev` pour web, `tsx watch src/index.ts` pour api/worker).
- `pnpm worker:once` — exécute une seule fois toutes les sources du worker puis quitte (équivalent `RUN_ONCE=true tsx src/index.ts` dans `apps/worker`). Ajouter `RUN_ONLY=<slug>` pour ne lancer qu'un seul job (ex. `RUN_ONCE=true RUN_ONLY=adresses tsx src/index.ts`).
- `pnpm build:web` — build statique Astro (`apps/web/dist`).
- `docker-compose up --build` — stack complète (Postgres/PostGIS, api, worker, Caddy) ; nécessite un `.env` basé sur `.env.example` (variables `POSTGRES_*`, `SITE_DOMAIN`).
- Régénération des extraits de relief 3D (cf. `carte.ts` ci-dessous), à ne relancer que si la zone couverte doit changer (données Mapterhorn statiques, pas de mise à jour périodique nécessaire) : télécharger le CLI [go-pmtiles](https://github.com/protomaps/go-pmtiles/releases), puis générer les deux extraits utilisés en relais l'un de l'autre par `enregistrerProtocolePmtiles` (`carte.ts`) —
  - fond global z0-12 (`apps/web/public/relief/aigoual.pmtiles`, ~60 Mo, Copernicus GLO-30) : `pmtiles extract https://download.mapterhorn.com/planet.pmtiles apps/web/public/relief/aigoual.pmtiles --bbox=3.2,43.8,4.1,44.4 --maxzoom=12` ;
  - extrait HD z13-15 (`apps/web/public/relief/aigoual-hd.pmtiles`, ~2 Go, LiDAR HD IGN via l'archive régionale Mapterhorn `6-32-23.pmtiles` qui couvre le sud de la France) : `pmtiles extract https://download.mapterhorn.com/6-32-23.pmtiles apps/web/public/relief/aigoual-hd.pmtiles --bbox=3.2,43.8,4.1,44.4 --maxzoom=15`. Le nom de l'archive régionale dépend de la position de la bbox du territoire dans le maillage z6 de Mapterhorn (`https://s3.us-west-2.amazonaws.com/us-west-2.opendata.source.coop/mapterhorn/mapterhorn/download_urls.json` liste les archives disponibles avec leurs bornes) ; à revérifier si `territoire.ts` change de bbox.
- Il n'y a ni linter ni suite de tests configurés dans ce dépôt — ne pas inventer de commande `lint`/`test`.

## Architecture

Le flux général : `apps/worker` ingère les données de sources externes → Postgres/PostGIS ; `apps/api` (Fastify) sert ces données ; `apps/web` (Astro + île Svelte MapLibre) les affiche. `packages/shared` (`@opendata-vda/shared`) est le socle commun (constantes de territoire, accès Postgres, migrations).

**`packages/shared/src/territoire.ts`** est le point d'édition unique pour réutiliser le projet sur un autre territoire : code INSEE, EPCI, bbox, liste des communes membres, et `CATALOGUE_SOURCES` (catalogue des sources open data avec slug/URL/licence/fréquence/`theme`). Ce fichier est référencé à la fois par le worker, l'api et le front.

**`packages/shared/src/sections.ts`** définit `SECTIONS` : la taxonomie des 13 rubriques du site (territoire, population, économie, finances, géographie, météo, environnement, risques, services, tourisme, mobilité, démocratie, sources), chacune avec `slug`/`titre`/`description`/`couleur`. Le champ `theme` de chaque entrée de `CATALOGUE_SOURCES` référence un `slug` de `SECTIONS`, ce qui permet à chaque page de section de lister ses propres sources et à `/sources` de regrouper le catalogue par domaine. Exposé en sous-chemin `@opendata-vda/shared/sections` (comme `./territoire`) pour être importable côté client sans tirer `pg`.

**Modèle de données** (`db/migrations/001_init.sql`), en 4 schémas Postgres/PostGIS :
- `territoire.communes` — polygones et métadonnées des communes (commune principale + membres EPCI).
- `couches.objets` — table générique point/polygone, clé `(couche, external_id)`, `props` jsonb + géométrie ; c'est la destination de la quasi-totalité des sources du worker (une ligne = un objet d'une couche donnée).
- `series.piezo` — chroniques de mesures piézométriques, clé `(code_bss, date)`.
- `meta.sources` / `meta.fetch_log` — catalogue et journal des exécutions.
- `meta.migrations` est créée au runtime par `migrate.ts` (n'existe pas dans le fichier SQL) pour suivre les migrations déjà appliquées.
- `db/migrations/002_recherche.sql` ajoute les extensions `pg_trgm`/`unaccent` et la vue `couches.lieux_recherche` (communes + objets nommés, `props->>'nom'`/`props->>'lieu'`) utilisée par la recherche tolérante aux fautes.

**`packages/shared`** (barrel `src/index.ts`) :
- `db.ts` — unique point d'accès Postgres : `createPool`, `upsertCommune`, `upsertObjet` (un objet), `upsertObjetsEnLot` (upsert par lots via `unnest`, pour les sources à forte volumétrie comme les adresses BAN), `upsertPiezoMesures`, `logFetchStart`/`logFetchEnd`. Utilisé à la fois par l'api et le worker.
- `migrate.ts` — `runMigrations` applique automatiquement, au démarrage de l'api et du worker, tout fichier `.sql` de `db/migrations` non encore enregistré dans `meta.migrations`. Il n'y a pas de commande de migration séparée.
- `geo.ts` — `corrigerCoordonnees` corrige une inversion lon/lat constatée ponctuellement sur une station Hub'Eau ; rejette le point si la correction ne retombe pas dans la bbox du territoire.

**`apps/worker`** :
- `src/scheduler.ts` définit `JOBS`, le registre unique associant un slug de source, une expression cron, et une fonction `run(pool): Promise<number>`. Pour ajouter une source : créer un fichier dans `src/sources/*.ts` exportant `run`, puis l'ajouter à `JOBS`.
- Chaque source fait ses propres appels `fetch` vers une API publique (geo.api.gouv.fr, Géorisques, Hub'Eau, API Carto IGN, Annuaire éducation/administration, Overpass/OSM, BAN) et upsert le résultat via `packages/shared/src/db.ts`. Les 12 sources actuellement enregistrées dans `JOBS` : `adresses` (BAN, détaillée ci-dessous), `apicarto` (cadastre, API Carto IGN), `education` (annuaire éducation nationale), `entreprises` (établissements SIRENE via Recherche d'entreprises), `geoapi` (contours commune/EPCI/15 communes membres, geo.api.gouv.fr), `georisques` (risques naturels/technologiques), `hubeau` (stations et chroniques piézométriques), `lannuaire` (annuaire de l'administration), `metaSources` (peuple `meta.sources` depuis `CATALOGUE_SOURCES` — pas un appel externe), `osm` (POI via Overpass), `rpg` (parcelles agricoles, Registre Parcellaire Graphique en WFS IGN, millésime codé en dur à relever annuellement), `signes_qualite` (aires AOC/AOP/IGP, CSV INAO).
- `src/sources/adresses.ts` ingère la Base Adresse Nationale : télécharge l'export CSV gzip départemental (`adresse.data.gouv.fr/data/ban/adresses/latest/csv/adresses-30.csv.gz`), le décompresse et le parse en streaming (`node:zlib` + `node:readline`, jamais bufferisé en entier), filtre sur les 15 codes INSEE de `COMMUNES_EPCI`, puis upsert par lots de 1000 via `upsertObjetsEnLot`. Les props n'incluent volontairement aucune clé `nom`/`lieu` pour ne pas polluer la vue `couches.lieux_recherche`. Une purge (`delete ... where maj < début_du_run`) supprime les adresses disparues de la BAN à chaque exécution complète.
- `runJob` encadre chaque exécution avec `logFetchStart`/`logFetchEnd` (résultat consigné dans `meta.fetch_log`, y compris en cas d'erreur).
- `src/index.ts` applique les migrations, fait un run complet de tous les jobs au démarrage du conteneur (ou une seule fois si `RUN_ONCE=true`, filtrable à un seul job via `RUN_ONLY=<slug>`), puis planifie les jobs récurrents via `node-cron`.

**`apps/api`** (Fastify) :
- Chaque module de `src/routes/*.ts` enregistre ses routes sur l'instance Fastify passée depuis `src/index.ts`.
- `routes/couches.ts` est générique : elle sert n'importe quelle couche déclarée dans `CATALOGUE_SOURCES` en GeoJSON via `/api/couches/:slug/geojson`, avec les slugs validés contre un `Set` — pas besoin d'ajouter une route par couche.
- `routes/outils.ts` héberge `/api/alti` (proxy altimétrie IGN, sans persistance) et `/api/recherche?q=` : fusionne en parallèle (`Promise.allSettled`) la BAN (`autocomplete=1`, biais géographique sur le centre du territoire, résultats post-filtrés sur les 15 codes INSEE de l'EPCI puisque la BAN n'accepte qu'un seul `citycode`) et une recherche floue sur la vue `couches.lieux_recherche` (`pg_trgm`/`unaccent`, `word_similarity`). Réponse unifiée `{ resultats: [{ type, couche, label, sousLabel, lon, lat, score }] }`, triée par score.
- `routes/territoire.ts` héberge `/api/territoire` : commune principale + géométries/population des 15 communes EPCI (depuis `territoire.communes`) + coordonnées du mont Aigoual ; consommée par l'accueil et `MapExplorer`.
- `routes/piezo.ts` héberge `/api/piezo/chronique?code_bss=&depuis=` : chronique de mesures depuis `series.piezo`.

**`apps/web`** (Astro, `output: "static"`) :
- `src/pages/index.astro` (accueil — hero, chiffres clés calculés au build depuis `@opendata-vda/shared`, grille des sections issue de `SECTIONS`, encart sources avec lien vers `/sources`) et `src/pages/carte.astro` (la carte plein écran). Une page par section de `SECTIONS` (`territoire.astro`, `population.astro`, `economie.astro`, `finances.astro`, `geographie.astro`, `meteo.astro`, `environnement.astro`, `risques.astro`, `services.astro`, `tourisme.astro`, `mobilite.astro`, `democratie.astro`) monte `src/layouts/SectionLayout.astro` avec `slug={"..."}` ; celui-ci affiche l'en-tête de la section, un `<slot>` (contenu par défaut « en préparation » si la page ne fournit rien) et, si `CATALOGUE_SOURCES` contient des entrées pour ce `theme`, un bloc `SourcesDomaine`. `src/pages/sources.astro` affiche le catalogue complet groupé par section. `src/components/SiteHeader.astro`/`SiteFooter.astro` habillent toutes les pages (nav avec menu déroulant « Thèmes » listant les 12 sections + lien `Sources` ; pied de page avec plan du site complet) ; la carte reste sans header global (son propre bandeau `.entete` fait office de retour à l'accueil).
- **`population.astro`** et **`economie.astro`** sont les sections à contenu réel : `population.astro` affiche les chiffres clés (population EPCI, nb communes) + une île `CarteThematique` sur la couche `adresse` (BAN) clusterisée ; `economie.astro` affiche trois cartes `CarteThematique` — établissements SIRENE clusterisés (couche `entreprise`), parcelles agricoles RPG (couche `parcelle_agricole`), signes de qualité AOC/AOP/IGP (couche `signe_qualite`). **`geographie.astro`** affiche une carte `CarteThematique` en relief 3D (`relief3d`) centrée sur le mont Aigoual.
- `src/lib/carte.ts` centralise les constantes cartographiques partagées entre îles : `IGN_WMTS`/`BASEMAPS`/`GEOLOGIE_WMS` (fonds IGN + géologie BRGM), `COULEUR`/`NOM_COUCHE` (mapping couche → couleur/libellé, indépendant de `CATALOGUE_SOURCES` côté back — à maintenir en cohérence manuellement), `ajouterCoucheClusterisee` (source GeoJSON `cluster: true` + layers clusters/compteur/points individuels, réutilisable pour toute couche à forte volumétrie), et les helpers de relief 3D `enregistrerProtocolePmtiles`/`activerRelief`/`reglerExagerationRelief`/`desactiverRelief` (source `raster-dem` terrarium servie via le protocole personnalisé `aigoualdem://{z}/{x}/{y}` — pas d'appel réseau externe au runtime ; le proxy `/api/alti` de l'IGN ne fournit qu'une altitude ponctuelle et n'est pas utilisable comme source de terrain). Ce protocole route deux archives PMTiles ouvertes en parallèle via `new PMTiles(...)` : le fond global `apps/web/public/relief/aigoual.pmtiles` (z0-12, ~30 m/pixel) sous z13, l'extrait HD `apps/web/public/relief/aigoual-hd.pmtiles` (z13-15, LiDAR HD IGN, ~3-4 m/pixel) au-delà, avec repli sur la tuile ancêtre z12 du fond global si la tuile HD est absente (bord de bbox) pour éviter tout trou de relief.
- L'île interactive `src/islands/MapExplorer.svelte`, montée en `client:only="svelte"` (pas de SSR) sur `/carte`, pilote une carte MapLibre GL complète (fonds IGN WMTS, calque géologie BRGM en WMS, panneau de couches, recherche, popups/fiches, toggle « Relief 3D » avec slider d'exagération). Au montage, elle consomme `/api/territoire`, `/api/couches` puis `/api/couches/:slug/geojson` pour chaque couche non vide, ajoutant une source/layer MapLibre par couche ; la couche `adresse` est rendue clusterisée (`ajouterCoucheClusterisee`) via un groupe « Adresses » désactivé par défaut (`GROUPES_ACTIFS_DEFAUT`).
- `src/islands/CarteThematique.svelte` est une île carte légère et réutilisable pour les pages de section (props `couches`, `cluster`, `hauteur`, `afficherContours`, `relief3d`) : fond IGN plan seul, contours du territoire optionnels, une couche par slug fourni, popups simples construites en DOM (jamais de HTML interpolé) ; `relief3d` active le terrain 3D avec caméra initiale inclinée.
- `src/islands/RechercheLieux.svelte` est un composant de recherche autonome (autocomplete à la frappe, debounce, navigation clavier, pattern ARIA combobox) qui interroge `/api/recherche` et émet un événement `selection` consommé par `MapExplorer` (`flyTo` + marqueur temporaire).
- En dev, `astro.config.mjs` proxifie `/api` vers `http://localhost:3000` (Fastify) pour que `pnpm dev:web` fonctionne sans Caddy.

**Déploiement** : `docker-compose.yml` + un Dockerfile par app + `Caddyfile`. Chaque Dockerfile fait un `pnpm install --filter <app>...` ciblé (n'installe que cette app et ses dépendances du workspace). `api` et `worker` tournent directement via `tsx` en production (pas de build JS compilé) ; seule `web` est buildée (`astro build`) et servie en statique par Caddy, qui reverse-proxy `/api/*` vers le service `api` (voir `Caddyfile`).
